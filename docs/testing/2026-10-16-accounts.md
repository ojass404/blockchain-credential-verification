# Database authentication and account isolation — 16 October 2026

## Implemented and exercised

SQLite accounts, institutions, server sessions, private PDF BLOBs and pending/confirmed action records are implemented. Seeded one administrator, two institution operators (distinct institutions/wallets) and two students (one per institution). Random passwords exist only in ignored `.local/seed-accounts.json`; password hashes are in the ignored owner-only database. No private keys are stored by the app.

`npm test --prefix backend`: **10 test groups passed** (six original verification groups plus four authentication/security groups). Authentication tests verify:

- Unauthenticated private API requests return 401.
- Role injection at login does not alter the database-assigned student role.
- Students cannot provision users; institution operators cannot approve institutions.
- Student A can download their own PDF, but Student B receives 404 for it; the reverse also fails.
- Institution A cannot download Institution B's PDF or prepare issuance for Student B.
- Administrator access and creation of student accounts with explicit institution membership work.
- Password values differ from stored salted hashes; SQLite data survives closing/reopening.
- Wallet verification requires the assigned address; signatures for a different wallet fail.
- Challenges cannot be reused, transferred to a second login session or used after expiry.
- Wallet verification is required before issuance; students cannot request wallet challenges.
- Invalid CSRF headers and cross-origin mutations fail with 403.
- Logout and expiration invalidate sessions. Cookie flags include HttpOnly and SameSite=Strict.
- Incorrect and nonexistent-account login attempts return the same generic error and no cookie.
- A marked seeded database is refused in production mode.

`npm run demo:accounts --prefix backend`: **passed against the actual current local contract and HTTP API**, using signatures from unlocked local-development signers only in this CLI. The API has no such signing capability. Both institution accounts signed ownership challenges, then signed real issuance transactions. The backend rejected the unrelated deployment transaction when supplied as an issuance receipt. Correct mined transactions were accepted. Students downloaded their own synthetic PDFs and were denied each other's. Institution A's attempt to revoke B's record was rejected at the API; a direct Solidity call was also rejected. A's legitimate revocation succeeded, and unauthenticated public verification reported A revoked and B active. Running this demo twice left four synthetic private certificate records for inspection.

`npm run build --prefix frontend`: **passed**, 171 modules transformed. Dependency installation audit reported zero vulnerabilities. No contract source or permission rules were changed in this iteration; the 21 contract tests passed in the prior iteration and the new CLI additionally exercised live cross-institution rejection.

## Browser observations

Signed in with the seeded student, institution and administrator accounts through the actual login form. Each received the correct dashboard with no role selector at login. Student A saw only their certificates. Institution A's issuance form listed only Student A, and issuance was disabled until wallet ownership proof. The administrator saw both institutions and all five accounts. Logout returned to the login form. Clicking wallet verification in a browser without an injected wallet displayed an actionable extension/network message, with no privileged action completed.

## Limits

Browser extension transaction prompts could not be exercised in the in-app browser, which has no injected Ethereum wallet. The same signature, transaction-preparation and receipt-confirmation backend path was exercised using the real local-wallet CLI. No mocked blockchain successes were used. Production hosting, password recovery/MFA, account deactivation, at-rest database encryption, quotas/pagination, and operational backups are outside this iteration. Dashboard status is explicitly labelled as last confirmed application state; public verification reads live chain state. Seed credentials and private PDFs/databases are not committed. No public deployment, push, or team-review claim is made.
